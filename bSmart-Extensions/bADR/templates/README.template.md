# Architecture Decision Records

This directory contains the architectural decisions that shape this project.

## When to use an ADR

Write an ADR when a decision has durable consequences for repository structure, module boundaries, public interfaces, data flow, runtime/startup behavior, compatibility, deployment, or maintainability. Do not use one for routine implementation choices.

## How to use this directory

1. Read this index and related records before making a significant architectural change.
2. Copy [`template.md`](template.md) to the next sequential number, using a short kebab-case title.
3. Record the context, decision, alternatives, consequences, scope, and related decisions.
4. Link the ADR from the implementation change, issue, or workstream document.
5. Once accepted, do not rewrite its historical decision. Mark it `Superseded` and create a new ADR when the decision changes.

## Status values

`Proposed` · `Accepted` · `Rejected` · `Deprecated` · `Superseded`
